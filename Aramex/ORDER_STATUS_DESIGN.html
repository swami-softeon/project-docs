01What this does

An order's real progress lives scattered across half a dozen tables — pick pre-plans, cartons, pre-cartons, detail lines. Answering "where is this order?" used to mean joining all of them. This system keeps the answer denormalized on the order itself, maintained in real time by triggers.

Two layers of columns were added. On order_header, a set of quantity and status columns describing the whole order. On order_detail, the same idea per order line — because a single line can be fully picked and packed while the rest of the order lags behind.

Each layer ends in one composite column — ord_derived_status on the header and ord_line_derived_status on the line — holding a single code from 100–370 that names the lifecycle state in plain language ("Part Allocated / Part Picked", "Loaded", "Cancelled Externally"). That code is what screens and reports read.

The three things that happen on every change

  1. A quantity moves. A source table changes; a trigger applies the delta to the order line, and a second trigger rolls the line delta up to the header.
  2. Component statuses recompute. Each quantity is compared against its denominator to produce a 0/1/2 tier — not started, partial, complete.
  3. The derived status recomputes. All component statuses are fed into one shared function that returns the composite code.
Reading the tiers

Almost every status column uses the same scale: 0 nothing yet · 1 partial · 2 complete. Allocation adds a fourth value, −1, meaning no allocation has even been attempted yet — which is genuinely different from "we tried and got nothing".

ord_qty, ASSIGNED_qty and shipped_qty already existed on order_detail and are written by the application — only allocated_qty had to be added.

No sub-status on the line

There is deliberately no line-level equivalent of ord_sub_status or ord_genl_status. A line inherits those from its parent order. That is what lets one shared function compute both levels, and it means order-wide states ("Order Grouped", "Cancelled Internally") automatically read the same on every line.

The join that ties a line to everything else

Cartons and pre-cartons don't reference order lines directly. They reach them through work_group2_dtl, always on the same three columns:

Column naming trap

ppcn_hdr / ppcn_dtl key on ppcn_no and gate on pcn_authorize_qty. Their batch counterparts batch_ppcn_hdr / batch_ppcn_dtl key on ppcn_id and gate on qty. Same structure, different column names.

04Quantities

Three quantities are tracked, and all three follow the same two-hop path: a source writes the line, and the line rolls up to the header. The header is always the sum of its lines — never computed independently.

Why line-first

Allocation originally wrote the header directly. Routing it through the line means the header is now provably the sum of its lines for all three quantities, the work_group2_dtl join lives in exactly one place, and the integrity package can cheaply check header totals against line totals.

05Component statuses

Six component statuses feed the derived status. Three come from quantities, three from the state of cartons and pre-cartons. Each is computed at both levels — the difference is always the denominator and the scope.

Allocation

The only status with four values. −1 is the starting point and survives until the warehouse has actually finished trying to allocate — signalled by every active pre-carton for the order reaching status ≥ 12. At that moment the rollup package flips −1 to 0, which is how "Did Not Allocate" becomes distinguishable from "Awaiting Allocation".

ValueMeaningCondition
−1No attempt yetNo active pre-cartons, or the lowest pre-carton status is still below 12
0Attempted, nothing allocatedAttempt complete and allocated quantity is zero (or the denominator is zero)
1Partially allocatedAllocated is above zero but below the denominator
2Fully allocatedAllocated reaches the denominator

Picking

0 when nothing is picked, 1 while picked is below the denominator, 2 when it reaches it. An ord_sub_status of 70 forces 2 outright — the warehouse declaring the pick finished overrides the arithmetic.

Shipping

Deliberately coarser: any shipped quantity at all is 1. Only ord_sub_status = 80 produces 2. Shipping is confirmed by the shipping process, not inferred from quantities.

Packing and loading

Both are driven by pcn_hdr.status, which is a ladder: ≥ 50 means packed, ≥ 60 means loaded — so a carton at 60 is also packed. status = 0 means cancelled and is excluded from every aggregate.

LevelRuleReaches 2 when
Order 1 as soon as any active carton of the order reaches the step Only from ord_sub_status ≥ 75 (pack) or = 78 (load)
Line 2 when all active cartons containing that line have reached the step; 1 when only some have All of the line's own cartons — regardless of the order's other cartons

This is the point of tracking lines at all. One line's cartons can all be loaded while another line of the same order is still being packed, and each line now reports its own truth. A line with no cartons is never promoted — cartons are created at pick time, so no carton means the line cannot have been packed or loaded.

Release

Computed from pre-cartons — ppcn_hdr and batch_ppcn_hdr combined, counting only rows with status ≠ 0 that have at least one authorized detail line. The threshold is status ≥ 18.

ResultCondition
0No active pre-cartons in scope
1The highest status has reached 18, but the lowest has not
2Every active pre-carton has reached 18

At order level the scope is every pre-carton of the order. At line level it is only the pre-cartons whose detail rows map to that line. One override applies at both levels: if the allocation status is 0 — attempted and nothing allocated — release is forced back to 0, because nothing can be released when nothing was allocated.

General status

Order-level only, and about provenance and cancellation rather than progress. Set to 12 on insert when the creating user is API, otherwise 11. When ord_sub_status later moves to 0 it becomes 1 (cancelled by API) or 2 (cancelled internally); ord_sub_status = 5 marks an empty order as 5.

06Derived status

One function, calc_derived_status, turns nine inputs into one code. It reads no tables, so both the header and the line call the same code path — the line simply passes its own component statuses alongside the parent order's sub, general and delivery status.

Evaluation order matters

The function is a single CASE: rules are tested top to bottom and the first match wins. Cancellation and the terminal sub-statuses are checked before anything else, so they cannot be overridden by stale component values.

Open item — delivery status codes

Codes 330, 340 and 350 are matched against the exact literals ATTEMPTED_DELIVERY, DELIVERY_ACCEPTED and DELIVERY_REJECTED, case-sensitively. A design note on file instead calls for case-insensitive matching against space-separated values. Until that is resolved, any delivery code stored in a different form will fall through to 320 (Shipped Complete).

07Lifecycle walkthrough

One order, start to finish, naming the trigger that fires at each step.

Order created insert into order_header

T_armx_ORDER_HEADER_INS_GEN_STATUS stamps the general status — 12 for an API-created order, 11 for one keyed internally.

Header reads 110 Created Externally; lines are still at their defaults.

Grouped, then routed ord_sub_status → 40 → 50

Each change fires T_armx_ORDER_HEADER_SUB_STATUS_UPD, which recomputes the header inline, and T_armx_ORDER_HEADER_LINE_CASCADE_UPD, which pushes the new sub-status down to every line.

Header and all lines read 130, then 140.

Released to the floor ord_sub_status → 60

Nothing has been allocated yet, so allocation status is still −1 everywhere.

Header and lines read 145 Awaiting Allocation.

Allocation runs ppcn_pick_pre_plan rows appear

  • T_armx_PPCN_PICK_PRE_PLAN_ALLOC_UPD resolves each row to an order line and adds its quantity.
  • T_armx_ORDER_DETAIL_LINE_STATUS_UPD moves that line's allocation status to 1 or 2 and recomputes its derived status.
  • T_armx_ORDER_DETAIL_ALLOC_QTY_UPDATE carries the delta to the header, and T_armx_ORDER_HEADER_DERIVED_STATUS_UPD refreshes the header code.

Lines that got stock read 160 or 190; lines that got none stay at 145 until the attempt completes, then become 150.

Pre-cartons released ppcn_hdr.status → 18 or beyond

T_armx_PPCN_HDR_RELEASE_STATUS_UPD (or its batch twin) calls p_armx_order_release_rollup, which recomputes release status for the order and, separately, for each line from its own pre-cartons.

Fully released lines read 230 Released; the order reads 200 until the last pre-carton follows.

Picking order_detail.ASSIGNED_qty rises

T_armx_ORDER_DETAIL_LINE_STATUS_UPD updates the line; T_armx_ORDER_DETAIL_PICK_QTY_UPDATE rolls the delta to the header.

Reads move through 240 Part Picked; once the warehouse sets sub-status 70, 260 Picked Complete.

Packing and loading pcn_hdr.status → 50 → 60

T_armx_PCN_HDR_PACK_LOAD_STATUS_UPD calls p_armx_order_pack_load_rollup. The header moves to 1 as soon as any carton reaches the step; each line moves to 2 only once all of its own cartons have.

A line whose cartons are all loaded reads 290 In Loading while its neighbours may still read 270 In Packing.

Confirmed and shipped ord_sub_status → 75 → 78 → 80

The sub-status trigger forces pack, load and ship status to 2 in turn, and the cascade trigger applies the same to every line.

Header and lines read 280, then 300, then 320 Shipped Complete.

Delivery outcome stop1_delv_status_cd set

T_armx_ORDER_HEADER_DERIVED_STATUS_UPD fires on the delivery code itself, and the cascade trigger carries it to the lines.

Final read: 330, 340 or 350.

08Backfill & integrity

p_armx_order_status_integrity recomputes everything from the source tables, ignoring whatever is currently stored. Use it after installing, after a bulk data load, or whenever a status looks wrong.

ProcedureWhat it does
recompute_line One line. Re-sums its allocation, re-derives all six component statuses and the line derived status.
recompute_order One order. Recomputes every line first, then derives the header quantities as the sum of those lines before recomputing the header statuses.
recompute_all Every order. Disables the six self-referencing triggers for the duration, commits every 1000 orders, re-enables them at the end — including on failure — and reports counts of processed, updated and errored rows.

Each procedure writes with a single guarded UPDATE that compares every column first, so a row that is already correct is not touched and generates no redo. Errors on one order are logged and skipped rather than aborting the sweep.

Lines before header, always

Because the header quantities are defined as the sum of the lines, the order matters: recompute_order refreshes the lines, then sums them. Running it also gives you a free consistency check — if a header total was drifting from its lines, this is what corrects it.

09Design constraints

Four rules shaped nearly every structural decision here. They are worth understanding before changing anything.

A trigger cannot read its own table

Oracle raises ORA-04091 when a row-level trigger queries the table it fires on. Two features needed exactly that — "have all pre-cartons been released?" and "have all cartons containing this line been packed?" — so both became compound triggers: collect the affected order keys row by row, then do the aggregation once the statement has finished. T_armx_PCN_HDR_PACK_LOAD_STATUS_UPD and the two release triggers all follow this shape, and each delegates the real work to a package so the logic exists once.

Self-updates must be BEFORE triggers

Every trigger that sets a column on the table it fires on is a BEFORE trigger assigning to :NEW, never an UPDATE statement — again to avoid the mutating-table error. Triggers that write a different table (the quantity rollups) are AFTER triggers issuing a normal UPDATE.

UPDATE OF watches the statement, not the values

An UPDATE OF col trigger fires based on which columns the issuing statement names — not on which :NEW values another trigger happened to change. So when a BEFORE trigger sets component statuses itself, the derived-status trigger will not pick them up, and that trigger has to recompute the derived status inline. This is why the sub-status and std_sku_qty triggers each carry their own copy of the derived status logic.

The same mechanism keeps the header and line triggers from looping: their UPDATE OF column lists do not overlap. The cascade fires only on sub, general and delivery status; the line triggers write only quantities and component statuses.

Status never steps backwards

Pack, load and release only ever move forward within a trigger path. A carton reverting or being cancelled will not knock a completed status back down, and a status already forced to 2 by the sub-status is preserved. The integrity package is the deliberate exception — it recomputes from scratch and is the tool for correcting a value that genuinely should come down.
