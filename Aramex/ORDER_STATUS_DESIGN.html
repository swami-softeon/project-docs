01What this does

An order's real progress lives scattered across half a dozen tables — pick pre-plans, cartons, pre-cartons, detail lines. Answering "where is this order?" used to mean joining all of them. This system keeps the answer denormalized on the order itself, maintained in real time by triggers.

Two layers of columns were added. On order_header, a set of quantity and status columns describing the whole order. On order_detail, the same idea per order line — because a single line can be fully picked and packed while the rest of the order lags behind.

Each layer ends in one composite column — ord_derived_status on the header and ord_line_derived_status on the line — holding a single code from 100–370 that names the lifecycle state in plain language ("Part Allocated / Part Picked", "Loaded", "Cancelled Externally"). That code is what screens and reports read.

The three things that happen on every change

  1. A quantity moves. A source table changes; a trigger applies the delta to the order line, and a second trigger rolls the line delta up to the header.
  2. Component statuses recompute. Each quantity is compared against its denominator to produce a 0/1/2 tier — not started, partial, complete.
  3. The derived status recomputes. All component statuses are fed into one shared function that returns the composite code.
Reading the tiers

Almost every status column uses the same scale: 0 nothing yet · 1 partial · 2 complete. Allocation adds a fourth value, −1, meaning no allocation has even been attempted yet — which is genuinely different from "we tried and got nothing".

No sub-status on the line

There is deliberately no line-level equivalent of ord_sub_status or ord_genl_status. A line inherits those from its parent order. That is what lets one shared function compute both levels, and it means order-wide states ("Order Grouped", "Cancelled Internally") automatically read the same on every line.

Why lines being added and removed matters

Lines can be created and deleted at any point until the order ships, so the three delta triggers above — which only watch UPDATE — are not enough on their own. Without the insert/delete trigger, deleting a picked line left the header's quantities permanently overstated; without the insert arm on the line-status trigger, a newly added line kept a derived status of 0, which is not a valid code.

04Quantities

Three quantities are tracked, and all three follow the same two-hop path: a source writes the line, and the line rolls up to the header. The header is always the sum of its lines — never computed independently.

Why line-first

Allocation originally wrote the header directly. Routing it through the line means the header is now provably the sum of its lines for all three quantities, the work_group2_dtl join lives in exactly one place, and the integrity package can cheaply check header totals against line totals.

05Component statuses

Six component statuses feed the derived status. Three come from quantities, three from the state of cartons and pre-cartons. Each is computed at both levels — the difference is always the denominator and the scope.

Allocation

The only status with four values. −1 is the starting point and survives until the warehouse has actually finished trying to allocate — signalled by every active pre-carton for the order reaching status ≥ 12. At that moment the rollup package flips −1 to 0, which is how "Did Not Allocate" becomes distinguishable from "Awaiting Allocation".

ValueMeaningCondition
−1No attempt yetNo active pre-cartons, or the lowest pre-carton status is still below 12
0Attempted, nothing allocatedAttempt complete and allocated quantity is zero (or the denominator is zero)
1Partially allocatedAllocated is above zero but below the denominator
2Fully allocatedAllocated reaches the denominator

Picking

0 when nothing is picked, 1 while picked is below the denominator, 2 when it reaches it. An ord_sub_status of 70 forces 2 outright — the warehouse declaring the pick finished overrides the arithmetic.

Shipping

Deliberately coarser: any shipped quantity at all is 1. Only ord_sub_status = 80 produces 2. Shipping is confirmed by the shipping process, not inferred from quantities.

Packing and loading

Both are driven by pcn_hdr.status, which is a ladder: ≥ 50 means packed, ≥ 60 means loaded — so a carton at 60 is also packed. status = 0 means cancelled and is excluded from every aggregate.

LevelRuleReaches 2 when
Order 1 as soon as any active carton of the order reaches the step Only from ord_sub_status ≥ 75 (pack) or = 78 (load)
Line 2 when all active cartons containing that line have reached the step; 1 when only some have All of the line's own cartons — regardless of the order's other cartons

This is the point of tracking lines at all. One line's cartons can all be loaded while another line of the same order is still being packed, and each line now reports its own truth. A line with no cartons is never promoted — cartons are created at pick time, so no carton means the line cannot have been packed or loaded.

Release

Computed from pre-cartons — ppcn_hdr and batch_ppcn_hdr combined, counting only rows with status ≠ 0 that have at least one authorized detail line. The threshold is status ≥ 18.

ResultCondition
0No active pre-cartons in scope
1The highest status has reached 18, but the lowest has not
2Every active pre-carton has reached 18

At order level the scope is every pre-carton of the order. At line level it is only the pre-cartons whose detail rows map to that line. One override applies at both levels: if the allocation status is 0 — attempted and nothing allocated — release is forced back to 0, because nothing can be released when nothing was allocated.

General status

Order-level only, and about provenance and cancellation rather than progress. Set to 12 on insert when the creating user is API, otherwise 11. When ord_sub_status later moves to 0 it becomes 1 (cancelled by API) or 2 (cancelled internally); ord_sub_status = 5 marks an empty order as 5.

06Derived status

One function, calc_derived_status, turns nine inputs into one code. It reads no tables, so both the header and the line call the same code path — the line simply passes its own component statuses alongside the parent order's sub, general and delivery status.

Evaluation order matters

The function is a single CASE: rules are tested top to bottom and the first match wins. Cancellation and the terminal sub-statuses are checked before anything else, so they cannot be overridden by stale component values.

08Backfill & integrity

p_armx_order_status_integrity recomputes everything from the source tables, ignoring whatever is currently stored. Use it after installing, after a bulk data load, or whenever a status looks wrong.

ProcedureWhat it does
recompute_line One line. Re-sums its allocation, re-derives all six component statuses and the line derived status.
recompute_order One order. Recomputes every line first, then derives the header quantities as the sum of those lines before recomputing the header statuses.
recompute_all Every order. Disables the six self-referencing triggers for the duration, commits every 1000 orders, re-enables them at the end — including on failure — and reports counts of processed, updated and errored rows.

Each procedure writes with a single guarded UPDATE that compares every column first, so a row that is already correct is not touched and generates no redo. Errors on one order are logged and skipped rather than aborting the sweep.

Lines before header, always

Because the header quantities are defined as the sum of the lines, the order matters: recompute_order refreshes the lines, then sums them. Running it also gives you a free consistency check — if a header total was drifting from its lines, this is what corrects it.

09Design constraints

Four rules shaped nearly every structural decision here. They are worth understanding before changing anything.

A trigger cannot read its own table

Oracle raises ORA-04091 when a row-level trigger queries the table it fires on. Two features needed exactly that — "have all pre-cartons been released?" and "have all cartons containing this line been packed?" — so both became compound triggers: collect the affected order keys row by row, then do the aggregation once the statement has finished. and the two release triggers all follow this shape, and each delegates the real work to a package so the logic exists once.

Self-updates must be BEFORE triggers

Every trigger that sets a column on the table it fires on is a BEFORE trigger assigning to :NEW, never an UPDATE statement — again to avoid the mutating-table error. Triggers that write a different table (the quantity rollups) are AFTER triggers issuing a normal UPDATE.

UPDATE OF watches the statement, not the values

An UPDATE OF col trigger fires based on which columns the issuing statement names — not on which :NEW values another trigger happened to change. So when a BEFORE trigger sets component statuses itself, the derived-status trigger will not pick them up, and that trigger has to recompute the derived status inline. This is why the sub-status and std_sku_qty triggers each carry their own copy of the derived status logic.

The rule that keeps it acyclic

Triggers run in both directions — lines roll up to the order, and the order cascades down to its lines. Nothing loops, and that is not luck. It holds because two column sets are kept disjoint:

EdgeWritesCould it fire the opposite edge?
line → order picked_qty, shipped_qty, allocated_qty and their statuses No — the cascade watches only sub, general, delivery status and std_sku_qty
order → line the five ord_line_*_status columns No — the three quantity rollups watch only ASSIGNED_qty, shipped_qty, allocated_qty

Both intersections are empty, so every chain terminates within two statements. The cascade does write line pack and load status, which the line-status trigger watches — but that trigger is BEFORE and only assigns :NEW, so it issues no statement and the chain cannot extend.

Invariant — check this before adding a trigger

A line trigger must never write a column the cascade watches, and the cascade must never write a column that a header-writing line trigger watches. Break either half and the two directions start feeding each other.

Reopening an order

There is one deliberate exception to forward-only movement. If std_sku_qty increases on an order already at sub-status 70, 75 or 78, the order is reopened to sub-status 60 so the added quantity can still be allocated and picked. The reopen happens before the pick status is recomputed, so pick status drops from a forced 2 back to a real comparison against the new denominator.

Because the issuing statement only names std_sku_qty, neither the sub-status trigger nor the line cascade would normally notice — hence std_sku_qty appears in the cascade trigger's watch list, so the reopen reaches the lines too.

The reopen also demotes pack and load status from 2 to 1, on the order and on every line — LEAST(status, 1), which only ever pulls a 2 down and never touches a 0 or a 1. It demotes rather than clears, because the cartons genuinely are still packed or loaded; what stopped being true is only that the step was complete. Those columns reach 2 in the first place because the sub-status was 75 or 78, so reverting below 75 removes the one thing that justified calling them complete.

Demoting instead of clearing matters for what the derived status reports next. An order reopened from 70, 75 or 78 always lands on 170 Part Allocated / Part Picked — deliberately, and only there. Codes 270 "In Packing" and 290 "In Loading" still require alloc = 2 AND release = 2, unconditionally: those labels are only trustworthy if allocation has genuinely finished, and a reopened order's allocation has not (raising the quantity is what dropped it back to 1). Rule 170 is instead widened to accept any pack/load value for exactly this case — it is also the more honest label, since it says plainly that allocation needs attention rather than implying packing is progressing normally. The carton-derived value returns on the next carton event, or on the next recompute.

This was tried the other way first, and it was wrong

An earlier version of this design relaxed 270/290 instead of widening 170, so that "In Packing" would still show even though allocation was incomplete. That is backwards: it makes the label lie about the one thing it exists to guarantee. The fix keeps 270/290 strictly gated and lets 170 absorb the reopened state instead — the label changes to reflect what actually needs attention.

Status never steps backwards

Pack, load and release only ever move forward within a trigger path. A carton reverting or being cancelled will not knock a completed status back down, and a status already forced to 2 by the sub-status is preserved. The integrity package is the deliberate exception — it recomputes from scratch and is the tool for correcting a value that genuinely should come down.

11Testing

Two tests prove the rules on a throwaway order. A read-only check tells you whether real data currently obeys them. A separate driver fixes the data that doesn't, in batches, without taking the triggers offline.

Regression test —

Drives a single order through its entire lifecycle and asserts the derived status after every step, printing PASS / FAIL per assertion and a summary. Roughly fifty assertions covering creation, allocation, release, picking, the reopen, line insert and delete, delivery codes and cancellation.

It is safe to run against a populated schema. It clones an existing order into a new order number using %ROWTYPE — so it needs no knowledge of your mandatory columns and never touches a real order — and it ends with ROLLBACK, leaving the database exactly as it found it. Edit the three constants at the top, then:

SetTo
c_company_noyour company
c_src_ord_noany existing order with at least two lines — it is only read
c_test_ord_noan order number that does not exist yet

It sets release, pack and load status directly rather than through cartons — proving the decision table and the cascade, but not the rollup packages. Those are the next file's job.

Carton-driven test —

Covers the three statuses the first file cannot: release, pack and load. Fully synthetic — it builds its own order, work group, cartons and pre-cartons, exercises them, and rolls everything back. It reads no real order and locks no live carton. Every insert clones an existing row of the same table with %ROWTYPE and overrides only the keys and linking columns, so it needs no knowledge of your mandatory columns or check constraints. Objects are numbered from 999990.

It walks the whole ladder: allocation through ppcn_pick_pre_plan so the real work-group join is exercised, pre-cartons to 12 then 18, a partial pick, one carton packed then all of them, loading, a cancelled carton, sub-status 75 and 78 forcing completion, and finally the reopen. Around sixty assertions, each naming an exact expected value.

Every expected code was checked against the rules first

The ten derived codes this test asserts — 145, 190, 200, 230, 240, 270, 290, 280, 300 and 170 — were each verified against the decision table before the test was finished, not after it ran. One was wrong on the first pass: with nothing picked, a reopen lands on 230, not 170. Rather than weaken the assertion, the fixture gained a picking step so it exercises the path that actually occurs in production.

Running them in a GUI client

Both scripts are written for SQL*Plus, and two things in them do not survive a graphical client such as SQLTools, DBeaver or SQL Developer. The SET lines are SQL*Plus commands those clients do not understand — and more importantly, they do not display DBMS_OUTPUT at all, which is where every PASS and FAIL was being written. Run the file as-is in SQLTools and you would see nothing.

So results are also written to a table, armx_test_result, through an autonomous transaction. That commits the log independently of the test, which is what lets the results survive the test's own ROLLBACK — and it makes the output an ordinary query that works in any client. Run once to create the table and its logging package.

StepDo this
1Run 02_test_harness.sql once, ever
2Edit the constants at the top of the test file
3Select from DECLARE to the final END; — not the trailing / — and execute it as one statement
4Run the RESULTS queries at the bottom of the file

The last of those returns a single row: passed, failed, and a verdict. The one above it lists only the failures, with the expected and actual value side by side.

The only autonomous transaction in the project

It exists solely so test output can escape a deliberate rollback. Nothing in the status triggers or rollup packages uses one — which is what makes the tests' ROLLBACK genuinely complete.

Integrity checks —

Read-only, and the faster of the two to work with. Section A returns a scoreboard: one row per check with a count of offending rows, all of which should be zero. Anything non-zero has a matching drill-down in section B. Section C dumps one order end to end — header, lines, cartons, pre-cartons, and a verdict on whether its stored status still matches the rules.

Seventeen checks, in four families: the header quantities equal the sum of their lines; every derived status is populated and exists in codes_dtl_master; each stored status still matches what the rules produce today; and the cross-status rules hold — nothing released without allocation, no completion flag set below its sub-status, no −1 allocation sentinel on an order that already has quantity.

The most useful query in the file

Drill-down B9 lists the component combinations that match no rule, grouped by how many orders sit in each. Those are the states where the derived status silently freezes at its previous value. It turns an invisible gap in the decision table into a ranked to-do list — start at the top.

Fixing existing orders —

p_armx_order_status_integrity.recompute_all exists, but it disables six triggers with ALTER TRIGGER, which is global, not session-scoped — for its whole duration every order the application touches goes unmaintained, and nothing catches up afterwards. It also commits every 1000 orders with no record of where it stopped, and reports only through DBMS_OUTPUT.

This driver recomputes one order at a time instead, through the ordinary recompute_order call, so every trigger stays enabled and the system can stay live. Progress lives in a queue table you can query mid-run, each order commits on its own, and a failure is recorded against that order rather than stopping the batch.

The one cost of staying live

With triggers enabled, each recompute_order fires , which stamps modify_tstamp. Every order this driver touches gets a new modify timestamp — something recompute_all avoids by disabling that trigger first. If a delta feed, interface or audit trail reads modify_tstamp, that is worth knowing before running this. load_queue_stale keeps the blast radius to the rows that are actually wrong, which is normally a small fraction of the table.
