How Claude Code Loads Context

Skills, instructions and memory all end up in the model's context window — but they get there by different routes, are written by different people, and are scoped differently. Here is the whole mechanism in one page.

Audience: developers using Claude Code Paths shown for Windows

The core idea

An eager index, and a lazy body

Everything Claude Code knows about your setup falls into one of two buckets. Grasping this split explains almost every behaviour that follows — including why a skill sometimes doesn't fire.

Eager — always loaded

In context before you type a single word, on every session, paid for on every turn.

  • System prompt and core tool schemas
  • Skill names and one-line descriptions
  • The full CLAUDE.md chain
  • The MEMORY.md index
  • Subagent and MCP server descriptions
  • Environment: working directory, date, git state
Lazy — loaded on demand

Only a pointer sits in context. The content is fetched at the moment it becomes relevant.

  • Skill bodies (SKILL.md)
  • Scripts and reference files bundled in a skill
  • Individual memory files
  • Deferred tool schemas
  • CLAUDE.md files in subdirectories

This is why a skill listing costs almost nothing: fifty skills contribute about fifty lines. A skill's two-hundred-line body only enters context if the skill is actually invoked.

It is also why the description line is the most important line in a skill. It is the only part Claude sees until the skill fires. A brilliant skill with a vague description never runs.

Session start

What happens, in order

The steps below run every time you open a new session. Solid markers are eager; hollow markers are the lazy hooks that stay dormant until something triggers them.

  1. System prompt, environment, core tools

    Harness rules, the working directory, today's date, git status, and the schemas for the built-in tools. Not user-editable.

  2. Skill directories are scanned

    User-level, project-level and bundled skills are merged into one flat list. Only the YAML frontmatter — name and description — is read.

  3. The CLAUDE.md chain is walked and concatenated

    Managed policy first, then the user-level file, then the project file at the working directory and every parent folder up the tree. Full text, verbatim.

  4. The memory index is read

    Just MEMORY.md — one line per stored fact. The individual memory files stay on disk.

  5. Settings are merged

    Managed, user, project and local settings combine into the session's model, permissions, environment variables and hooks. This shapes behaviour rather than adding text to context.

  6. MCP servers connect

    Each server contributes its instructions and its tool names. Larger tool schemas are deferred until searched for.

  7. … then, during the conversation

    Your request matches a skill description, so the skill body loads. An index line looks relevant, so that memory file is read. A subdirectory with its own CLAUDE.md is touched, so that file loads. Each of these is a decision made mid-turn, not a search.

There is no semantic search at runtime. Retrieval is Claude reading a short eager index and choosing to open something. If a description or an index line is vague, the content behind it effectively does not exist.

The three surfaces

What belongs where

Instructions, memory and skills are easy to confuse because all three end up influencing behaviour. They separate cleanly on two questions: who writes it, and when it loads.

Instructions

CLAUDE.md · written by you

Loads
Always, in full
Answers
“How should you behave here, always?”
Cost
Every turn, every session
Put here
  • Build, test and run commands
  • Conventions not inferable from the code
  • Where things live — the orientation you'd give a new hire
  • Hard prohibitions
  • Output and tone preferences
Not here
  • Anything discoverable by reading the code
  • Long procedures for occasional tasks
  • Facts about a person rather than the work

Memory

Markdown files · written by Claude

Loads
Index always, file when relevant
Answers
“What have we established?”
Cost
About one line per fact
Put here
  • user — role, expertise, standing preferences
  • feedback — a correction or confirmed approach, with its reason
  • project — goals and constraints not derivable from the repo
  • reference — links, dashboards, ticket ids
Not here
  • Anything the repo or git history already records
  • Anything that only matters for today's conversation
  • Secrets and credentials

Skills

SKILL.md folders · written by you

Loads
Description always, body on invoke
Answers
“How do I carry out task X?”
Cost
About one line per skill
Put here
  • A repeatable task with a specific method
  • The exact commands to run
  • The output format and presentation rules
  • Known gotchas
  • Bundled scripts and reference files, loaded only when needed
Not here
  • Standing behaviour — a skill is inert until triggered
  • Genuinely one-off tasks

Writing a good skill description. Cover what it does, when to use it, and the words a person would actually type. It is the entire retrieval signal — treat it as the interface, not the label.

Scope

User level versus workspace level

Every surface exists at two levels. User-level applies in every project you open; workspace-level applies only inside that folder. Where both exist, the narrower one wins for single values, while permission lists are additive.

ConcernUser level — all workspacesWorkspace level
Instructions~/.claude/CLAUDE.md<project>/CLAUDE.md plus parent and sub folders
Skills~/.claude/skills/<project>/.claude/skills/
Settings~/.claude/settings.json.claude/settings.json shared, settings.local.json personal
Slash commands~/.claude/commands/<project>/.claude/commands/
Subagents~/.claude/agents/<project>/.claude/agents/
Plugins~/.claude/plugins/—
Memoryno user-level tier~/.claude/projects/<path-slug>/memory/
Transcripts—~/.claude/projects/<path-slug>/*.jsonl

~ is Unix shorthand for your home folder. On Windows that resolves to C:\Users\<you>, so the user-level instruction file lives at C:\Users\<you>\.claude\CLAUDE.md. If you create it in Notepad, check it did not save as CLAUDE.md.txt — Explorer hides known extensions by default.

Memory in detail

Automatic, but selective

Memory is the one surface Claude writes for itself, which makes it the one people misunderstand most. Two separate things are worth separating:

The folder is created for you automatically, one per workspace. The files are written by Claude during conversations, whenever it judges something worth keeping — or whenever you say “remember that…”.

So automatic means the model decides and writes, not the system records everything. It is deliberately selective: the bar is that a fact will still matter weeks from now and is not already recoverable from the code or the git history. The files are plain markdown, so you can read, edit or delete them yourself at any time.

The shape on disk

  • One fact per .md file, with frontmatter carrying a name, a description used for recall, and a type of user, feedback, project or reference.
  • MEMORY.md is the index — one line per fact, and the only part loaded every session.
  • Files cross-reference each other with [[slug]] links.

Memory is keyed to the folder path. The directory name under projects/ is your working directory, slugified — so D:\dev\UI becomes D--dev-UI.

Two consequences. Renaming or moving a project orphans its memory, and a new empty one is created. And memory never crosses workspaces: a preference recorded in one project is invisible from every other. If you want a rule honoured everywhere, it belongs in the user-level CLAUDE.md, not in memory.

In practice

Where does this go?

When you have something you want Claude to know, work down this list and stop at the first match.

Must it apply on every turn, whatever the topic? CLAUDE.md
Is it a fact to recall when it becomes relevant? memory
Is it a procedure for a certain kind of task? skill

The most common mistake is the first two blurring together. A standing rule such as “always show me the SQL before running it” often ends up recorded as a memory in whichever project it came up in — which means it silently stops applying the moment you open a different folder. Rules go in instructions; facts go in memory.
